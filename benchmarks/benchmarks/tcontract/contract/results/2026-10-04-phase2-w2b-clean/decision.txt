# W2b clean confirmation on an idle host (Phase 2, tprims-rs #50)

Follow-up to `../2026-10-03-phase2-w2b/decision.txt` (#58). That decision was
taken on a loaded host with the b0 mode measured on one case only; this is the
quiet-host run.

## Protocol

Branch `phase2-w2b-results` (`c70d1dc`); binary built from it (tprims `36bad52`
plus the committed `contract.rs` change). Two sessions, s1 and s2; corpora
`tenferro-p1-gemm` (53 cases) and `large-batched-gemm` (16); modes `separate_b1`
and `separate_b0`; widths 1T/4T/8T; `BENCH_RUNS=5`. Each run is pinned to an
idle 8-core set and accepted only if those cores were idle before and after
(`pinned.sh`); the driver waited for the set to go idle again. Raw CSVs and logs
are in `s1/` and `s2/`, both sessions complete.

`ratio = packed exec / plan exec`; `> 1` means the shipped plan is faster.

## Verdict for W2b's fitting mode (`separate_b1`): no change needed

No faer-routed case is below 0.95 beyond the A/A noise, in either session:

| corpus | session | 1T | 4T | 8T | A/A on packed-routed (mean / worst) |
|---|---|---|---:|---:|---|
| tenferro-p1-gemm | s1 | 0 | 0 | 1 | 0.019 / ×1.23, 0.039 / ×1.26, 0.083 / ×1.51 |
| tenferro-p1-gemm | s2 | 0 | 1 | 0 | 0.031 / ×1.24, 0.075 / ×1.61, 0.057 / ×1.39 |
| large-batched-gemm | s1 | 0 | 0 | 0 | 0.014 / ×1.05, 0.018 / ×1.04, 0.025 / ×1.08 |
| large-batched-gemm | s2 | 1 | 0 | 0 | 0.037 / ×1.18, 0.044 / ×1.16, 0.017 / ×1.04 |

The three flagged cases are inside the session's own spread or negligible:
`gemm_batched_047` 8T 0.93 (A/A worst ×1.51), `gemm_batched_050` 4T 0.81 at
faer 6 us (launch overhead), `large_b1_m4096_n4096_k4096` 1T 0.92 at faer 3.19 s.
Faer-routed workload `packed/plan` is 1.02-1.17 (faer faster) at every width.
**The `separate_c_pays` threshold fitted in W2b stands.**

## `separate_b0` exposes the lazy `beta == 0` faer route

In `separate_b0` every separate-C problem is faer-routed: 24 of 53
(tenferro-p1-gemm) and 8 of 16 (large-batched) by the ordinary faer strategy,
and the remaining 29 / 8 by the W2b lazy route (`PlanReport::beta_zero`, taken
when `separate_c_pays` is false). The lazy cases lose to the packed driver at
4T/8T:

* tenferro-p1-gemm, lazy faer-routed cases below 0.95: **2 at 1T, 11 at 4T,
  17 at 8T** (s1) and 3 / 10 / 12 (s2). Worst: `_026` 0.46-0.68, `_029`
  0.51-0.75, `_032` 0.57-0.84, `_003` 0.57-0.82.
* large-batched-gemm: 0 / 1 / 5 (s1) and 0 / 3 / 6 (s2); worst
  `large_b512_m128_n128_k128_f64` 0.55-0.56.

These are reproducible: the same case's ratio agrees between s1 and s2 within a
mean `|log|` of 0.044 / 0.069 / 0.084 (worst ×1.34 / ×1.34 / ×1.46) at
1T/4T/8T, far inside the observed losses.

Calls-weighted effect on tenferro-p1-gemm, comparing the lazy route against
routing those cases to packed:

| width | s1 never/current | s2 never/current |
|---|---:|---:|
| 1T | 1.047 | 1.062 |
| 4T | 0.985 | 0.991 |
| 8T | 0.976 | 0.967 |

So the lazy route is worth 5-6% at 1T and costs 1-3% at 4T/8T. On
large-batched-gemm it is a wash (1.007 / 1.002 / 0.994).

## Cross-check: the losses are the faer engine's, not W2b's

The same 53 cases measured in the default `overwrite` mode, where there is no C
at all and faer is chosen unconditionally by the plain-GEMM policy (`plan` row =
faer, `packed` row = the packed driver, current binary, idle 0-7):

| width | weighted packed/faer | faer-routed cases below 0.95 |
|---|---:|---|
| 1T | 1.068 | 2 (`_001`, `_017`) |
| 4T | 1.072 | 10 |
| 8T | 1.101 | 10 (`_001 _003 _011 _016 _017 _019 _023 _026 _029 _032`) |

The below-0.95 set is the same class as the lazy route's. So the
`beta == 0` lazy route is not a W2b-specific defect: it routes a separate-C
problem with no C term to the same engine the no-C policy would choose, and
that engine loses to the packed driver on these shapes at 4T/8T.

S0 measured this policy on the same corpus at 1.078 / 1.173 / 1.231
(pre-W1-W3); W1-W3 removed the packed driver's catastrophic batched-tiny cases,
so the same policy now reads 1.068 / 1.072 / 1.101 on a quiet host. Faer still
wins the calls-weighted workload at every width, but no longer by much, and
about ten cases now favour packed.

## Decision

The W2b criterion ("adjust the threshold if a faer-routed case drops below
0.95 beyond the A/A noise") is applied: **the lazy `beta == 0` faer route is
removed.** A separate C the rule declines is now packed for every `beta`, so
b0 follows b1's routing; `PlanReport::beta_zero` and the second dispatch are
gone.

Measured effect of removing it, from this session's own data (the packed row
is already the post-fix behaviour):

* tenferro-p1-gemm b0 workload, never/current: 1T 1.047 / 1.062 (slower),
  4T 0.985 / 0.991, 8T 0.976 / 0.967 (faster) — a wash overall;
* the cases this fix moves are no longer faer-routed, so the b0 lazy-route
  losses are gone; the residual b1/b0 cases under 0.95 are the ones already
  documented above, inside the session's A/A spread (`_047` 8T 0.93 at A/A
  worst x1.51, `_004` 1T 0.949);
* it gives up faer's 1T wins (up to 2.4x on `gemm_batched_008`) and, at 8T,
  `gemm_batched_013` (1.47), `_022` (1.78), `_025` (1.63), `_030` (1.24).

W4 is **not warranted** by this evidence: the remaining measured gap is which
engine serves a copy-free GEMM at 4T/8T, not the packed driver's barrier,
tiling or direct-B.

Open, not decided here: the **faer-vs-packed engine choice for copy-free GEMMs
at 4T/8T** (the cross-check above: about ten cases favour packed by up to 2x,
while the weighted workload still favours faer, 1.068 / 1.072 / 1.101). That is
the spec's "faer stays" decision, so it is a Phase 2 scope question.
