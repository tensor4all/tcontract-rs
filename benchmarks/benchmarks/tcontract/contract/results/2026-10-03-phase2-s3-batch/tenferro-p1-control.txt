W1 balance fix: why and what.
Regression (control-s1/s2, c71bba4 vs #54, two sessions, noise 1-4% on large cases): dot_general_001_f64 4T +24%, 8T +53%;
dot_general_032_f64 4T +21%. Cause: W1's rule sent LARGE items to batch lanes whenever H >= budget, also when H does not split
evenly over the lanes (001 and 032 have H = 9: on 8 lanes one lane runs two entries, critical path 2/9 against 1/8).
Fix (driver/batch.rs): for non-tiny items lanes need balance, H / (lanes * ceil(H / lanes)) >= 0.9, else the team keeps the item.
After the fix (table below): 001 0.989 / 0.989 / 1.042 and 032 4T 0.206 (a win) at 1T/4T/8T vs c71bba4.
Caveats: (1) the 'fix' binary is origin/main c49370c + this change, i.e. it also contains W2 (#56); '#54' is the W1 branch
binary (c71bba4 + W1). (2) the host was loaded by other users' jobs during this session (waits for idle cores, other
agents), and mid-size cases (10-60 ms at 1T, the whole 1T column below dot_general_013) swing +-30% between binaries that run the
same code path at 1T (budget 1: lanes() returns at once), so only the large, stable cases carry the conclusion.
(3) the 1T column is a no-regression check: large cases are 0.98-1.04.
Not W1: dot_general_036 at 8T (no batch axis) and a few small cases move with the binary, not with the rule.
