# avx512-ukr-asm — freeze the AVX-512 f64 24x8 real micro-kernel's assembly

Isolated experiment. It (a) freezes the compiler-generated AVX-512 x86-64
assembly of the f64 `24 x 8` real micro-kernel
(`tcontract_kernel::kernels::x86::avx512_f64::real::<3,8>`, family id
`avx512.f64.real.24x8`) into a checked-in `.S` file, (b) checks whether that
kernel is instruction-identical with and without `-C target-cpu=native`, and
(c) microbenchmarks the intrinsic kernel against the frozen-assembly kernel
under the project's measurement protocol.

## What is compared

The kernel body is generated by `macro_rules! simd_kernels` in
`crates/tcontract-kernel/src/kernels/macros.rs` and instantiated for
`avx512_f64` in `crates/tcontract-kernel/src/kernels/x86/avx512.rs`
(`MR = 3 * 8 = 24`, `NR = 8`). It is a column-major tile product:

```
ab[j*24 + i] = sum_p a[p*24 + i] * b[p*8 + j]      (a: 24*kc, b: 8*kc, ab: 24*8)
```

`real::<3,8>` is `#[target_feature(enable = "avx512f")]`, so the packed driver
reaches it through the function-pointer trampoline `tramp_real::<3,8>`. Under
`-C target-cpu=native` LLVM inlines `real` into `tramp_real`, so the
trampoline *is* the whole kernel body; that is the symbol `freeze.sh` freezes.

- **intrinsic arm** — `cfg_avx512_f64::real_config().ukr.func`, i.e. the exact
  `tramp_real::<3,8>` monomorphization the packed driver stores (no fresh
  monomorphization, no wrapper call added).
- **frozen arm** — `frozen_real_24x8`, the same body assembled from
  `asm/avx512_f64_real_24x8.S` and linked by `build.rs`.

## Build & run

```sh
# from this directory (already `-C target-cpu=native` via .cargo/config.toml)
cargo build --release
cargo run --release --bin selfcheck

# 1T on CPU 4 (never 0-3), pinned + idle-checked
benchmarks/scripts/pinned.sh 4 -- target/release/bench
```

`freeze.sh` regenerates `asm/avx512_f64_real_24x8.S` and
`asm/native-vs-baseline.diff` from scratch (builds `tcontract-kernel` twice with
`--emit=asm`); it is not needed to build or run the crate.

## Result: instruction identity (native vs baseline target)

**Refuted.** The two `--emit=asm` builds are *not* instruction-identical. The
FMA-loop instruction **multiset** is the same — per `k`-step 24 `vfmadd231pd`,
8 `vbroadcastsd`, 3 `vmovupd` loads, plus 24 stores and 24 accumulator zeroes
(118 body instructions total) — but the **code differs in three ways**:

1. **Scheduling.** `-C target-cpu=native` (znver5 model) reorders the
   `vbroadcastsd`/`vfmadd231pd` issue into `j = 1,2,0,3,4,5,6,7` to hide
   broadcast latency; `-C target-cpu=x86-64` (generic model) issues them in
   strict `j = 0..7` order.
2. **Mnemonic choice for the high registers.** baseline zeroes zmm16-23 with
   `vpxord` and stores them with `vmovdqu64`; native uses `vxorpd %xmmN` and
   `vmovupd` throughout (functionally identical, different encodings).
3. **Function structure.** native inlines `real` into `tramp_real` (one
   symbol); baseline cannot (no global avx512f), so `tramp_real` is a bare
   `jmp real::<3,8>` and `real` is a separate symbol.

See `asm/native-vs-baseline.diff`.

## Result: intrinsic vs frozen (1T, CPU 4, pinned, 7 reps, best-of)

`results/bench-1t.csv`, `results/bench-1t.guard`. Both kernels are
bit-identical to each other and to the naive reference (self-check passes).

| kc | intrinsic best_ns | frozen best_ns | ratio (intr/frozen) | GF/s |
|----|------------------:|---------------:|--------------------:|-----:|
| 16 | 117.04 | 116.89 | 1.001 | 52.5 |
| 64 | 466.41 | 466.32 | 1.000 | 52.7 |
| 256 | 1865.18 | 1865.34 | 1.000 | 52.7 |

The frozen kernel is **not slower**: the ratio is 1.000 within noise. Both sit
at ~52.7 GF/s ≈ 98 % of this host's AVX-512 FMA peak (Zen 5 executes one
512-bit FMA/cycle ≈ 16 flops/cycle × 3.35 GHz ≈ 53.6 GF/s), so the kernel is
FMA-throughput-bound and neither the instruction-identity differences nor the
LTO nuance below moves the number.

## Caveat: `--emit=asm` is pre-LTO

`cargo rustc … --emit=asm` on the lib dumps the **pre-LTO** codegen unit. The
frozen `.S` therefore keeps the un-unrolled `k`-loop (24 FMA/iteration).
The **linked** binary (thin-LTO, or `lto = false` as used here) additionally
unrolls the `k`-loop ×2 and adds a `kc == 1` fast path. The benchmark still
compares like-for-like in effect — both arms are FMA-bound — but a frozen
`.S` generated with `--emit=asm` is **not byte-identical to what the final
binary runs**; a faithful freeze of production code would have to be taken
from the linked object, not the `--emit=asm` intermediate.

## What freezing buys (and does not)

- **Buys:** an artifact you can audit, diff, and hand-annotate; a way to pin a
  specific codegen against a rustc/LLVM upgrade; and a vehicle for the
  instruction-identity question above (answer: not identical across
  `-C target-cpu`).
- **Does not buy:** a performance improvement (0.999–1.001 here), nor a
  distribution-independent kernel — the `.S` is still x86-64/AVX-512F-only,
  rustc/LLVM-version specific, and (as noted) only faithful to the *linked*
  code if you freeze post-LTO output.

## Layout

- `freeze.sh` — regenerate the `.S` + diff (builds twice, extracts, diffs).
- `asm/avx512_f64_real_24x8.S` — the frozen body (provenance in its header).
- `asm/native-vs-baseline.diff` — normalized instruction diff.
- `build.rs` — `cc -c` the `.S` and link it (no `cc` crate).
- `src/lib.rs` — extern decl, the two fn pointers, the naive reference.
- `src/bin/selfcheck.rs` — correctness (`kc` ∈ {0,1,2,3,7,16,33}, exact ints).
- `src/bin/bench.rs` — pinned 1T microbenchmark, CSV.
